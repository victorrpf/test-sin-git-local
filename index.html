¿Commit desde el editor o desde la web?

Una guía sencilla para entender por qué no es lo mismo subir archivos a GitHub arrastrándolos que trabajar con Git desde VS Code.

1. Para qué sirve trabajar con Git desde el editor

Cuando una tarea pide usar Git desde el editor, el objetivo no es simplemente «que los archivos aparezcan en GitHub». El objetivo es que practiques el flujo de trabajo que se usa de verdad en un entorno profesional: crear el repositorio, ir haciendo commits de tus cambios, publicarlos y mantener sincronizada tu copia local con la del servidor.

Ese flujo —crear, modificar, hacer commit, hacer push, hacer pull— es una habilidad en sí misma, independiente del resultado final. Por eso, aunque subir archivos desde la web produzca un repositorio con el mismo aspecto, no demuestra que hayas practicado ese flujo.

2. La diferencia entre un commit local y uno hecho en la web

Todo commit de Git guarda dos datos de identidad: el autor (quién escribió el cambio) y el committer (quién lo registró en el historial). En la mayoría de los casos ambos coinciden, pero no siempre.

  • Cuando haces un commit local desde VS Code, el committer eres tú, con el nombre y el correo que configuraste con git config.
  • Cuando subes o editas un archivo directamente en github.com, GitHub crea el commit por ti. En ese caso el committer no eres tú: es GitHub (web-flow), y GitHub firma ese commit con su propia clave criptográfica.

Esa diferencia queda registrada de forma permanente en el historial del repositorio, y es lo que permite distinguir un tipo de commit del otro.

3. Cómo se detecta, paso a paso

No hace falta ser un experto para comprobarlo. Estas son las señales, en orden:

  1. El mensaje del commit. Si subiste un archivo arrastrándolo con «Add file → Upload files», GitHub genera automáticamente el mensaje «Add files via upload», a menos que lo cambies a mano.
  2. La etiqueta «Verified». En la lista de commits, los hechos en la web suelen mostrar una etiqueta verde «Verified».
  3. El aviso al pulsar sobre esa etiqueta. Si haces clic encima, aparece el mensaje «This commit was created on GitHub.com», que confirma que el commit se generó desde el navegador.

Importante: un commit hecho desde tu editor también puede aparecer como «Verified» si has configurado tu propia firma GPG o SSH. La diferencia es que, en ese caso, el committer sigues siendo tú, no GitHub. Por eso conviene mirar siempre quién es el committer, no solo si aparece la etiqueta verde.

Además de mirar el historial en GitHub, puedes comprobarlo en tu propio equipo: abre el panel Source Control de VS Code. Si la carpeta del proyecto no aparece como un repositorio de Git, o si el Graph no muestra esos commits que buscas, es que ese trabajo no se hizo con Git en ese equipo.

Ojo: lo contrario no sirve como prueba de que sí se usó Git. Si en algún momento clonas el repositorio o haces un pull, los commits que se hicieron desde la web también aparecerán en tu Graph local, porque pasan a formar parte del historial compartido. Que aparezcan ahí no significa que se hayan creado desde el editor.

4. Qué se pierde al subir archivos desde la web

Más allá de que se detecte, trabajar solo desde la web tiene un coste real en el aprendizaje:

  • No practicas el ciclo básico de Git: stage, commit, push y pull.
  • No revisas los cambios antes de confirmarlos, algo fundamental para detectar errores antes de que queden en el historial.
  • No puedes trabajar sin conexión, algo habitual cuando se usa un editor local.
  • Corres el riesgo de que tu copia local del proyecto y la del repositorio remoto se desincronicen, lo que obliga después a fusionar cambios (y a entender cómo resolver un conflicto), una situación que conviene aprender a manejar de forma controlada.

5. Por qué afecta a la evaluación

Cuando una tarea pide trabajar con Git desde el editor, no basta con que el resultado final —los archivos en GitHub— tenga buen aspecto. El profesorado puede revisar el historial de commits y ver, con los indicios anteriores, cómo se hizo cada uno. Si los commits muestran que fueron creados en github.com, no se cumple el requisito de haber trabajado con Git desde el editor, aunque el contenido final sea correcto.

6. Cómo hacerlo bien

  1. Clona el repositorio en tu equipo usando VS Code (Clonar repositorio de Git).
  2. Haz los cambios que necesites en los archivos, con tu editor.
  3. Desde el panel Source Control, revisa los cambios, escribe un mensaje descriptivo y haz commit.
  4. Pulsa Sync Changes para publicar tu commit y mantener sincronizada tu copia local con la remota.
  5. Comprueba después en el historial de GitHub que tu commit no lleva la etiqueta de GitHub como committer: debe aparecer tu nombre, no «GitHub (web-flow)».
